1. The correct mental model

A FastAPI worker normally runs an event loop. Each async request progresses until it reaches an awaitable that is not ready. The loop then advances other requests. Async improves utilization during waiting. It does not make the underlying database, model inference, JSON encoding, or computation intrinsically faster. 

flowchart LR
    C[Clients] --> P[Load balancer / proxy]
    P --> W1[Uvicorn worker process]
    P --> W2[Uvicorn worker process]
    subgraph Worker 1
      EL[Single event loop]
      R1[Request A coroutine]
      R2[Request B coroutine]
      R3[Request C coroutine]
      TP[Bounded thread pool]
      EL --> R1
      EL --> R2
      EL --> R3
      R2 -->|sync endpoint / dependency| TP
    end
    R1 -->|await| DB[(Database)]
    R3 -->|await| API[Downstream API]
    TP --> FS[(File or blocking SDK)]

Concurrency

Multiple in-flight tasks make progress by yielding at await points. Best for I/O-heavy workloads.

Parallelism

Multiple CPU cores or processes execute at the same time. Needed for sustained CPU-heavy work.

Queueing

When demand exceeds any constrained resource, requests wait. This is the usual source of p95/p99 growth.

Core rule: an async def route is safe only when every potentially slow operation inside it either yields with await, is intentionally offloaded, or is demonstrably short and bounded.

2. Choosing def versus async def

Choose based on the libraries called by the route, not on a blanket project convention.

    C -- Yes --> E[Move to process / worker system]
    B -- Yes --> F{Does the library expose a real async API?}

    F -- No --> H{Can the whole callable be synchronous?}

@app.get("/users/{user_id}")

    return await session.get(User, user_id)

    return legacy_sdk.fetch(key)  # executed via the framework thread pool

# Good: isolate a blocking call within an otherwise async flow
from anyio import to_thread

@app.get("/mixed/{key}")
async def get_mixed(key: str):
    item = await async_cache.get(key)
    if item is None:
        item = await to_thread.run_sync(legacy_sdk.fetch, key)
    return item

3. Async caveats that cause production incidents

Critical

Blocking the event loop

requests.get(), sync DB drivers, time.sleep(), large local parsing, and blocking SDKs inside async def prevent that worker's loop from serving other requests.

Critical

Unbounded fan-out

Creating hundreds or thousands of tasks can overwhelm sockets, downstream services, connection pools, memory, and retry systems.

High

Thread-pool saturation

Sync endpoints, sync dependencies, file handling, and explicit thread offloads may share the same AnyIO capacity limiter. More offloading can simply move the queue.

High

Connection-pool mismatch

Request concurrency greater than available HTTP or database connections causes pool waiting. Oversized pools can overload the downstream instead.

High

Improper client lifecycle

Creating an HTTP client or DB engine per request discards connection reuse and adds repeated handshakes, authentication, DNS, and setup cost.

High

Unsafe shared sessions

A mutable transaction/session object should not be used concurrently across tasks. Use a session per request or per independent transaction.

Core

Cancellation swallowed

Suppressing CancelledError can leave work running after clients disconnect or deadlines expire. Cleanup should occur, then cancellation should normally be re-raised.

Core

Async generator cleanup

Streaming responses, generators, and resource dependencies need deterministic cleanup. Client disconnects are normal control-flow events, not only errors.

Core

Serial awaits disguised as async

Three independent calls awaited sequentially still take approximately the sum of their latencies. Concurrency must be explicit and bounded.

Core

Retries multiply load

Retries without a deadline, jitter, idempotency, and attempt limits amplify downstream failures and consume the remaining latency budget.

Core

Large response serialization

Validation and JSON serialization are CPU work. Large payloads can dominate endpoint time even when all I/O is asynchronous.

Core

Too many workers

Each process owns memory and often its own pools. Multiplying workers can accidentally multiply database connections, caches, model copies, and startup work.

4. Model latency as a budget and a queueing system

End-to-end latency includes more than handler execution. A route can have fast business logic and still be slow because it waits for a worker, thread token, socket, database connection, lock, rate limit, or downstream queue.

5. Where to focus first

Optimize in the following order. This prevents cosmetic tuning from hiding structural bottlenecks.

1

Find event-loop blocking

Search for sync network clients, sync DB drivers, time.sleep, filesystem operations, compression, parsing, and heavy transformations inside async def.

2

Reduce downstream work

Eliminate unnecessary calls, avoid N+1 queries, batch reads, parallelize only independent operations, cache stable data, and return less data.

3

Reuse clients and pools

Create HTTP clients, database engines, and other expensive transports once per worker during application lifespan.

4

Bound concurrency and queues

Use semaphores, pool limits, ingress limits, queue limits, and per-tenant limits. Unlimited concurrency converts latency into outages.

5

Enforce deadlines

Set an end-to-end deadline, derive tighter downstream timeouts, stop retrying when the remaining budget is insufficient, and propagate cancellation.

6

Optimize database and serialization

Inspect query plans, indexes, lock waits, transaction scope, model validation, response shape, pagination, and encoding cost.

7

Scale processes after efficiency

Add workers or replicas after verifying downstream capacity and per-process resource multiplication.

Decision rule: tune the resource whose queue grows first. Adding workers does not fix a saturated database, a slow dependency, or unbounded fan-out.

Lifespan-owned resources

from contextlib import asynccontextmanager
from fastapi import FastAPI
import httpx
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(
        timeout=httpx.Timeout(connect=1.0, read=3.0, write=2.0, pool=0.5),
        limits=httpx.Limits(
            max_connections=100,
            max_keepalive_connections=40,
            keepalive_expiry=20.0,
        ),
    )

    app.state.db_engine = create_async_engine(
        settings.database_url,
        pool_size=20,
        max_overflow=10,
        pool_timeout=1.0,
        pool_pre_ping=True,
    )
    app.state.session_factory = async_sessionmaker(
        app.state.db_engine,
        expire_on_commit=False,
    )

    try:
        yield
    finally:
        await app.state.http.aclose()
        await app.state.db_engine.dispose()

app = FastAPI(lifespan=lifespan)
Pool numbers are examples, not defaults for every system. Size them from measured concurrency, downstream limits, number of worker processes, and acceptable queue time.

7. Downstream HTTP calls

A shared async client provides connection pooling and avoids paying setup costs on every request.

    S --> P{HTTP connection pool}
    P --> D[Downstream service]
    D --> P
    P --> R
    S -.excess waits or is rejected.-> Q[Bounded queue]
    style S fill:#e9efff,stroke:#3157c8
    style P fill:#e5f7f8,stroke:#087f8c
    style Q fill:#fff3e7,stroke:#b65a10

Timeout layers

Set connect, read, write, and pool-acquisition timeouts. A single generic timeout can obscure which resource is constrained.

Connection limits

Keep limits aligned with downstream capacity. A high client limit can create a larger outage rather than lower latency.

Retries

Retry only when the operation is safe and the failure is transient. Include exponential backoff, jitter, attempt cap, and deadline awareness.

Response handling

For large payloads, stream or cap response size. Do not load unbounded remote content into memory.

from fastapi import Request, HTTPException
import httpx

@app.get("/profile/{user_id}")
async def profile(user_id: str, request: Request):
    client: httpx.AsyncClient = request.app.state.http
    try:
        response = await client.get(f"/users/{user_id}")
        response.raise_for_status()
        return response.json()
    except httpx.PoolTimeout as exc:
        # Local capacity is exhausted. Retrying immediately is usually harmful.
        raise HTTPException(503, "Dependency capacity unavailable") from exc
    except (httpx.ConnectTimeout, httpx.ReadTimeout) as exc:
        raise HTTPException(504, "Dependency timed out") from exc
    except httpx.HTTPStatusError as exc:
        raise HTTPException(502, "Dependency returned an error") from exc

8. Database access standards

One session per unit of work

Open a session for a request or transaction and close it deterministically. Do not share one session across tasks.

Short transaction scope

Do not hold a connection while calling external services, waiting for user input, or performing unrelated computation.

Pool wait is a signal

A pool timeout is not automatically a reason to increase pool size. Check long queries, lock waits, leaked sessions, and database limits first.

from collections.abc import AsyncIterator
from fastapi import Request
from sqlalchemy.ext.asyncio import AsyncSession

async def get_session(request: Request) -> AsyncIterator[AsyncSession]:
    factory = request.app.state.session_factory
    async with factory() as session:
        try:
            yield session
        except Exception:
            await session.rollback()
            raise

@app.post("/orders")
async def create_order(payload: OrderCreate, session: AsyncSession = Depends(get_session)):
    order = Order(**payload.model_dump())
    session.add(order)
    await session.commit()
    await session.refresh(order)
    return order

Do not make independent calls concurrently on the same session

# Avoid
await asyncio.gather(
    session.execute(query_a),
    session.execute(query_b),
)

# 2. Execute sequentially in the same transaction.

9. Parallel fan-out without overload

Concurrency should be explicit, structured, and limited. The fastest design is often fewer calls, not more tasks.

import asyncio

FANOUT_LIMIT = 8
fanout_sem = asyncio.Semaphore(FANOUT_LIMIT)

async def guarded_fetch(client, url: str):
    async with fanout_sem:
        return await client.get(url)

async def fetch_dashboard(client, urls: list[str]):
    # Python 3.11+: structured concurrency cancels sibling tasks on failure.
    results: list[object] = []
    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(guarded_fetch(client, url)) for url in urls]
    for task in tasks:
        results.append(task.result())
    return results
flowchart LR
    A[Request] --> B{Can calls be combined?}
    B -- Yes --> C[Batch / bulk API]
    B -- No --> D{Are calls independent?}
    D -- No --> E[Await sequentially]
    D -- Yes --> F{Is concurrency bounded?}
    F -- No --> G[Add semaphore / chunking]
    F -- Yes --> H[TaskGroup / gather]
    H --> I{Partial failure acceptable?}
    I -- No --> J[Fail fast and cancel siblings]
    I -- Yes --> K[Collect per-call results and errors]
Avoid: await asyncio.gather(*(call(x) for x in ten_thousand_items)). This eagerly creates a large number of tasks and transfers overload to memory, pools, sockets, or the dependency.

10. Deadlines, timeouts, and cancellation

A timeout is part of capacity control. It limits how long scarce resources remain occupied.

flowchart TD
    A[Request starts with deadline] --> B[Compute remaining budget]
    B --> C[Assign smaller downstream timeout]
    C --> D{Operation completes?}
    D -- Yes --> E[Continue]
    D -- No --> F[Cancel operation]
    F --> G[Release connection / lock / file]
    G --> H{Safe fallback exists?}
    H -- Yes --> I[Return degraded result]
    H -- No --> J[Return 504 / controlled error]
    J --> K[Do not retry past deadline]
          
import asyncio
from fastapi import HTTPException

async def build_response():
    try:
        async with asyncio.timeout(2.5):  # Python 3.11+
            return await assemble_from_dependencies()
    except TimeoutError as exc:
        raise HTTPException(504, "Request deadline exceeded") from exc

async def cancellable_operation():
    resource = await acquire_resource()
    try:
        return await resource.do_work()
    except asyncio.CancelledError:
        # Add structured logging if useful, but normally propagate cancellation.
        raise
    finally:
        await resource.close()

Budget hierarchy

Ingress deadline > handler budget > downstream attempt timeout. Leave time for cleanup, serialization, and response transmission.

Retry budget

Before retrying, check whether enough time remains for backoff plus another attempt. Otherwise fail or degrade immediately.

Thread offloading is not a universal async fix. It protects the event loop from blocking, but the work still consumes memory, threads, CPU, and possibly downstream connections. The thread pool itself becomes a bounded queue.

12. Background work: in-process versus durable

flowchart TD
    A[Work requested] --> B{Must it survive process restart?}
    B -- Yes --> C[Durable queue + worker]
    B -- No --> D{Is it small and bounded?}
    D -- Yes --> E[In-process background task]
    D -- No --> C
    C --> F[Idempotency key]
    C --> G[Retry / dead-letter policy]
    C --> H[Status tracking]
    E --> I[Still apply limits and observability]

In-process task

Suitable for best-effort, short operations where loss during restart is acceptable. It shares the web worker's resources.

Durable worker

Use for important, slow, retryable, CPU-heavy, or bursty work. Return a job identifier and expose status rather than holding the request open.

13. AKS target architecture and latency boundaries

The FastAPI process is only one stage in the request path. On AKS, tail latency can be introduced by the edge, ingress, Kubernetes service routing, pod admission, event-loop or thread contention, Azure service networking, database pools, and downstream throttling. Measure each boundary rather than treating pod CPU as the complete performance signal.

North-south path

Client, edge/WAF, load balancer, ingress, Service, and pod. Capture latency and status at both the edge and ingress.

East-west path

Pod-to-pod and pod-to-Azure-service traffic. DNS, SNAT, private endpoints, network policy, and TLS handshakes can dominate short requests.

Capacity path

HPA creates pods, the scheduler places them, and the cluster autoscaler adds nodes only when pods cannot be scheduled. These are separate control loops.

14. Pod sizing, Uvicorn workers, and connection budgets

Kubernetes already supplies process-level replication. For most async FastAPI APIs, begin with one server process per pod so resource limits, health, termination, and autoscaling map cleanly to one runtime. Scale pods before adding workers inside a pod. 

flowchart TD
    R[Incoming requests] --> SVC[Service load balancing]
    SVC --> PA[Pod A: one event loop]
    SVC --> PB[Pod B: one event loop]
    SVC --> PC[Pod C: one event loop]
    PA --> DBA[DB pool A]
    PB --> DBB[DB pool B]
    PC --> DBC[DB pool C]
    DBA --> DB[(Database connection limit)]
    DBB --> DB
    DBC --> DB
    HPA[HPA] -->|adds pods| PC
    CA[Cluster autoscaler] -->|adds node capacity when pending| NODE[AKS node pool]
    NODE --> PC

One worker per pod

Clear CPU and memory accounting, smaller failure domain, simpler graceful shutdown, and predictable connection pools. This is the preferred baseline.

Multiple workers per pod

Can improve CPU-core utilization for some workloads, but every worker duplicates the event loop, HTTP client, database pool, caches, and application memory.

Capacity equations that must be reviewed

# Maximum theoretical database connections
replicas × workers_per_pod × (pool_size + max_overflow)

# Maximum HTTP sockets to one client pool, if each worker owns a client
replicas × workers_per_pod × max_connections

# Approximate API admission capacity
replicas × workers_per_pod × per_worker_concurrency_limit

# Keep explicit headroom for:
# migrations, admin tools, failover, rolling surge pods, background workers,
# database maintenance, and other services sharing the dependency.

16. Autoscaling an async API without scaling the wrong signal

An I/O-heavy async API can be saturated while CPU remains moderate. CPU-only HPA is a useful baseline, but it may not detect event-loop delay, active-request pressure, connection-pool wait, or downstream throttling. 

sequenceDiagram
    participant Load as Request load
    participant Pod as FastAPI pods
    participant HPA as HPA or KEDA
    participant Sched as Kubernetes scheduler
    participant CA as AKS cluster autoscaler
    participant Nodes as Node pool
    Load->>Pod: concurrency rises
    Pod-->>HPA: CPU or custom metric rises
    HPA->>Sched: request more replicas
    alt node has capacity
      Sched->>Pod: place new pod
    else pod remains Pending
      Sched-->>CA: unschedulable pod
      CA->>Nodes: add node capacity
      Nodes-->>Sched: node becomes Ready
      Sched->>Pod: place new pod
    end

Signal selection

SignalUseful forCaveat
CPU utilizationCPU-heavy serialization, validation, compression, and mixed workloadsCan stay low while an async service is blocked on DB/HTTP pools or downstream latency.
Active requests or admitted concurrencyRequest-driven async APIs with a known safe per-pod concurrencyRequires application or ingress metrics and a custom-metrics path.
Queue depth and oldest-message ageService Bus workers and durable background processingUse KEDA for event-driven workers; do not hold synchronous HTTP requests open for queue processing.
Event-loop lagDetecting blocking code or CPU contentionExcellent alert and diagnostic signal; use cautiously as a direct autoscaling metric.
DB/HTTP pool waitFinding the true saturation pointScaling pods can make dependency exhaustion worse. Treat rising wait as a reason to cap admission or fix downstream capacity.
p95/p99 latencySLO monitoringLatency-based scaling is reactive and can oscillate. Prefer leading signals such as concurrency or queue depth.

AKS scaling standards

  1. Set resource requests before enabling CPU HPA; HPA utilization is calculated relative to requests.
  2. Keep a minimum replica buffer for sudden traffic because pod and node scale-out are not instantaneous.
  3. Enable and tune the AKS cluster autoscaler or node autoprovisioning so HPA-created pods can be scheduled.
  4. Size all DB and HTTP pools against maxReplicas, rolling-surge pods, and every worker process.
  5. Use a startup probe that remains false through import, model loading, migrations checks, and other startup CPU spikes so HPA does not learn from a half-ready pod.
  6. Use a slow scale-down stabilization window to avoid connection churn and repeated cold starts.
  7. Set a hard application admission limit. Autoscaling should complement backpressure, not replace it.
Do not scale through dependency collapse. If database checkout wait or downstream 429/503 rates are already rising, additional pods can multiply connections and retries. First cap concurrency, reduce fan-out, honor retry-after behavior, or expand the dependency under an explicit capacity plan.

17. Ingress timeouts, health probes, and graceful shutdown

A production request has multiple clocks. The outer infrastructure timeout must be longer than the application deadline, and the application deadline must leave time for cancellation, cleanup, and a controlled response. 

flowchart LR
    C[Client timeout 35s] --> E[Edge timeout 34s]
    E --> I[Ingress timeout 30s]
    I --> A[Application deadline 25s]
    A --> D1[DB budget]
    A --> D2[HTTP budget]
    A --> S[Serialization and response budget]
    D1 --> X[Cancel and clean up before 25s]
    D2 --> X
    S --> X

Timeout hierarchy

LayerStandardFailure if reversed
Client and edgeLonger than ingress, with retry behavior documentedClient gives up while AKS continues expensive work.
IngressLonger than application deadline but boundedIngress emits 504 before the application can return a controlled error.
ApplicationOne end-to-end deadline per requestIndependent downstream timeouts add up beyond the infrastructure limit.
DownstreamsBudgets derived from remaining application timeA late dependency consumes the entire request and prevents cleanup.
Long workReturn 202 and use Service Bus or another durable job systemLong open connections consume ingress, pod, and downstream capacity.

Termination flow during rollout or node drain

sequenceDiagram
    participant K as Kubernetes
    participant EP as Service endpoints
    participant P as FastAPI pod
    participant U as Uvicorn
    K->>P: mark pod Terminating and run preStop
    K->>EP: remove pod from routable endpoints
    P->>P: wait short drain buffer
    K->>U: send SIGTERM
    U->>U: stop accepting new requests
    U->>U: await in-flight requests up to graceful timeout
    U->>P: run lifespan shutdown and close pools
    K->>P: SIGKILL only if grace period expires

Readiness

False until clients, configuration, and required startup state are ready. Return false during deliberate drain when the implementation supports it.

Liveness

Cheap, local, and independent of remote dependencies. It should detect a process that cannot recover without restart.

Startup

Protects slow initialization from premature liveness failures and keeps warming pods out of HPA readiness calculations.

Grace period

Must exceed the drain buffer plus the maximum accepted request deadline plus resource cleanup margin.

Configure proxy headers only when the request comes through trusted proxies. Do not accept arbitrary forwarded headers from untrusted networks, because client IP and scheme information can be spoofed.

18. Azure identity, secrets, networking, and dependency access

Workload Identity

Bind a Kubernetes service account to a Microsoft Entra identity. Use DefaultAzureCredential or the relevant Azure SDK credential chain instead of client secrets in environment variables.

Key Vault

Fetch secrets through the Azure SDK or mount them with the Secrets Store CSI Driver. Plan secret rotation and application reload behavior explicitly.

Private connectivity

Use private endpoints and private DNS where required. Validate DNS resolution, routing, firewall rules, and egress paths from the pod network, not only from a developer laptop.

Egress capacity

High outbound concurrency can exhaust SNAT or downstream quotas. Reuse connections, prefer private connectivity, and use a planned NAT or firewall architecture.

20. AKS performance testing and safe rollout

Test through the same edge and ingress path used in production, and separately test the pod service from inside the virtual network. The difference reveals edge, TLS, ingress, DNS, and networking overhead.

Pod baseline

Fixed replicas, autoscaling disabled, one worker per pod. Establish service time, safe concurrency, memory, CPU, and pool behavior.

Ingress baseline

Repeat through the public or private ingress. Compare TLS, proxy, request-size, keep-alive, and upstream timing.

Autoscaling test

Start at minimum replicas, apply step and burst traffic, and measure time to HPA decision, pod scheduling, startup readiness, and useful capacity.

Failure test

Inject slow DB/API calls, 429/503 responses, DNS failure, node drain, pod termination, and Key Vault or telemetry unavailability.

Acceptance sequence

  1. Run correctness and cancellation tests for every endpoint before load testing.
  2. Find the per-pod concurrency knee where throughput stops scaling linearly or p99 rises sharply.
  3. Set Uvicorn admission, HTTP pools, DB pools, and HPA targets below that knee.
  4. Test at minReplicas, normal replicas, maxReplicas, and during one rolling-surge pod.
  5. Verify that HPA scale-out does not exceed database, cache, API, SNAT, or license quotas.
  6. Drain one pod under load and confirm no material error spike and no requests exceed the graceful-shutdown budget.
  7. Drain one node and verify topology spreading, PDB behavior, pending-pod duration, and cluster-autoscaler recovery.
  8. Run a soak test long enough to expose connection leaks, task leaks, file growth, DNS issues, and memory fragmentation.

Rollout standards

ControlStandardReason
Image referenceImmutable tag or digest; never deploy latestEnables deterministic rollback and auditability.
Rolling strategymaxUnavailable: 0 and bounded surge for latency-sensitive APIsPreserves capacity while avoiding an uncontrolled connection surge.
Readiness gateDo not route until initialization and required local state are completePrevents cold or broken pods from receiving production traffic.
Database changesBackward-compatible expand-and-contract migrations, run separately from pod startupAvoids every pod racing to migrate and blocking readiness.
CanaryUse a small traffic slice for material runtime, dependency, or schema changesDetects latency and pool regressions before full rollout.
RollbackAutomated or one-command rollback with image and configuration version recordedReduces time under a bad deployment.
Pass condition: the API remains within its latency and error SLO during burst traffic, pod rollout, one pod loss, and one node drain; overload remains bounded; and the service recovers without manual pod restarts after dependencies return to normal.

21. AKS-ready FastAPI service skeleton

This skeleton combines shared client lifecycle, readiness state, explicit health endpoints, bounded fan-out, deadlines, and controlled error translation. The values are illustrative and must be derived from SLOs and load tests. 

import asyncio
import os
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

import fastapi
import httpx
from azure.monitor.opentelemetry import configure_azure_monitor
from sqlalchemy.ext.asyncio import (
    AsyncSession,
    async_sessionmaker,
    create_async_engine,
)

# Initialize telemetry before constructing FastAPI objects.
if connection_string := os.getenv("APPLICATIONINSIGHTS_CONNECTION_STRING"):
    configure_azure_monitor(connection_string=connection_string)

FANOUT_LIMIT = int(os.getenv("FANOUT_LIMIT", "8"))
fanout_sem = asyncio.Semaphore(FANOUT_LIMIT)

@asynccontextmanager
async def lifespan(app: fastapi.FastAPI):
    app.state.started = False
    app.state.ready = False

    http = httpx.AsyncClient(
        timeout=httpx.Timeout(connect=1.0, read=2.0, write=2.0, pool=0.25),
        limits=httpx.Limits(
            max_connections=int(os.getenv("HTTP_MAX_CONNECTIONS", "80")),
            max_keepalive_connections=int(os.getenv("HTTP_KEEPALIVE_CONNECTIONS", "30")),
        ),
    )
    engine = create_async_engine(
        os.environ["DATABASE_URL"],
        pool_size=int(os.getenv("DB_POOL_SIZE", "10")),
        max_overflow=int(os.getenv("DB_MAX_OVERFLOW", "2")),
        pool_timeout=float(os.getenv("DB_POOL_TIMEOUT_SECONDS", "0.75")),
        pool_pre_ping=True,
    )
    session_factory = async_sessionmaker(engine, expire_on_commit=False)

    app.state.http = http
    app.state.engine = engine
    app.state.session_factory = session_factory
    app.state.started = True
    app.state.ready = True

    try:
        yield
    finally:
        # Uvicorn has stopped accepting new work and is completing graceful shutdown.
        app.state.ready = False
        await http.aclose()
        await engine.dispose()

app = fastapi.FastAPI(lifespan=lifespan)

@app.get("/health/live", include_in_schema=False)
async def live() -> dict[str, str]:
    return {"status": "alive"}

@app.get("/health/startup", include_in_schema=False)
async def startup(request: fastapi.Request) -> dict[str, str]:
    if not request.app.state.started:
        raise fastapi.HTTPException(status_code=503, detail="starting")
    return {"status": "started"}

@app.get("/health/ready", include_in_schema=False)
async def ready(request: fastapi.Request) -> dict[str, str]:
    if not request.app.state.ready:
        raise fastapi.HTTPException(status_code=503, detail="not ready")
    return {"status": "ready"}

async def get_session(request: fastapi.Request) -> AsyncIterator[AsyncSession]:
    async with request.app.state.session_factory() as session:
        try:
            yield session
        except Exception:
            await session.rollback()
            raise

async def limited_get(client: httpx.AsyncClient, url: str) -> dict:
    async with fanout_sem:
        response = await client.get(url)
        response.raise_for_status()
        return response.json()

@app.get("/aggregate/{entity_id}")
async def aggregate(
    entity_id: str,
    request: fastapi.Request,
    session: AsyncSession = fastapi.Depends(get_session),
):
    client: httpx.AsyncClient = request.app.state.http

    try:
        async with asyncio.timeout(2.8):
            db_entity = await session.get(Entity, entity_id)
            if db_entity is None:
                raise fastapi.HTTPException(404, "Entity not found")

            async with asyncio.TaskGroup() as group:
                profile_task = group.create_task(
                    limited_get(client, f"https://profile.internal/{entity_id}")
                )
                score_task = group.create_task(
                    limited_get(client, f"https://score.internal/{entity_id}")
                )

            return {
                "entity": EntityOut.model_validate(db_entity),
                "profile": profile_task.result(),
                "score": score_task.result(),
            }
    except TimeoutError as exc:
        raise fastapi.HTTPException(504, "Request deadline exceeded") from exc
    except httpx.PoolTimeout as exc:
        raise fastapi.HTTPException(503, "Downstream client saturated") from exc
    except httpx.TimeoutException as exc:
        raise fastapi.HTTPException(504, "Downstream timed out") from exc
    except httpx.HTTPStatusError as exc:
        raise fastapi.HTTPException(502, "Downstream failed") from exc
Do not run schema migrations in every pod's lifespan. Use a controlled deployment job or pipeline step and apply backward-compatible database changes so old and new pods can coexist during a rolling update.

22. AKS architecture and code-review checklist

FastAPI and event-loop safety
  • No blocking network, database, filesystem, sleep, or SDK call runs directly inside async def.
  • CPU-heavy work is moved to a separate worker, process, or inference service.
  • Fan-out, thread offload, HTTP connections, DB connections, retries, payloads, and deadlines are bounded.
  • HTTP clients and database engines are created once per worker process during lifespan.
Pod and process model
  • One Uvicorn worker per pod is the measured default, or multiple workers have documented benchmark evidence.
  • CPU, memory, and ephemeral-storage requests and limits are based on load and soak tests.
  • Connection budgets include max HPA replicas, worker count, max overflow, and rolling-surge pods.
  • Minimum replicas and topology spread meet the availability target.
  • Images run as non-root with dropped capabilities and no unnecessary write access.
Health and termination
  • Startup, readiness, and liveness probes have distinct meanings.
  • Liveness does not fail because a remote database or API is unavailable.
  • Readiness remains false until initialization is complete.
  • PreStop, endpoint removal, Uvicorn graceful timeout, and Kubernetes termination grace are load-tested together.
  • PodDisruptionBudget and rolling-update settings preserve required capacity.
Autoscaling and backpressure
  • HPA targets use valid resource requests and a signal aligned to the actual bottleneck.
  • Cluster autoscaler or node autoprovisioning can schedule HPA-created pods.
  • HPA scale-down stabilization prevents churn.
  • The API rejects overload predictably before memory, thread pools, or downstream pools collapse.
  • Queue workers use a separate Deployment and event-driven scaling where appropriate.
Ingress and networking
  • Ingress choice and support lifecycle are documented.
  • Client, edge, ingress, application, and downstream timeout hierarchy is consistent.
  • TLS, body-size limits, keep-alive, streaming, WebSocket, and forwarded-header requirements are explicit.
  • Private DNS, private endpoints, egress NAT/firewall, SNAT capacity, and network policy are tested from pods.
  • Ingress 499/502/503/504 metrics are correlated with application traces.
Azure identity and secrets
  • Pods use Microsoft Entra Workload ID rather than embedded client secrets.
  • Key Vault access follows least privilege and secret rotation behavior is tested.
  • Mounted secret changes are reloaded or trigger a controlled pod restart.
  • Telemetry or credential-provider failure cannot block the core request path indefinitely.
Observability and acceptance
  • Application traces include pod, namespace, node, version, request ID, and dependency correlation.
  • Dashboards include event-loop lag, CPU throttling, pool wait, pending pods, HPA status, ingress errors, and dependency throttling.
  • Alerts pair user-impact SLOs with cause signals.
  • Load tests run through ingress and directly inside the network.
  • Acceptance includes burst, soak, rolling update, pod drain, node drain, and slow-dependency scenarios.
