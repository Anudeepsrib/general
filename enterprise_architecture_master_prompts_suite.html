1. How to use the prompt suite

Use one prompt as the system instruction for the relevant task. Add repository files, architecture diagrams, manifests, traces, tickets, logs, acceptance criteria, and production constraints as user-provided evidence.

Architecture review

Use before a major release, migration, scale event, or cost-reduction initiative.

Feature delivery

Use from discovery through design, implementation plan, tests, rollout, and telemetry.

Bug investigation

Use for regressions, incidents, intermittent failures, latency spikes, and correctness defects.

Product strategy

Use to find workflow gaps, missing platform capabilities, adoption blockers, and strategic opportunities.

Do not paste production secrets. Remove credentials, tokens, personal data, private customer data, and confidential competitive data that is not necessary for the review.
A prompt cannot prove production readiness by itself. It must require evidence, explicit assumptions, tests, benchmark data, rollout controls, and rollback criteria.

8. Non-negotiable quality gates

        

          
DimensionRequired evidenceTypical failure

          
            
CorrectnessContracts, invariants, acceptance criteria, regression tests, data consistencyPerformance change alters business behavior or data freshness

            
SecurityAuthN/AuthZ, tenant isolation, secret handling, prompt-injection controls, auditabilityFeature or cache leaks cross-tenant or restricted data

            
Latencyp50, p95, p99, dependency spans, queue and pool wait, load-test profileAverage improves while tail latency or errors regress

            
ReliabilityTimeouts, retries, idempotency, load shedding, graceful degradation, rollbackRetries amplify outages or long workflows exhaust resources

            
OperabilityTracing, metrics, logs, alerts, dashboards, runbooks, ownershipNew behavior cannot be diagnosed in production

            
CostCost per request, model/token cost, storage/compute growth, scale behaviorFeature is technically valid but financially unbounded

            
MaintainabilityClear interfaces, bounded complexity, ownership, documentation, migration planFramework abstraction hides critical behavior or creates lock-in without value

          
        

      


      

        
9. Recommended evidence package for each prompt

        

          

            
Code and infrastructure

            
Repository tree, critical files, dependency lock, Dockerfile, AKS manifests, CI/CD, IaC, environment matrix, client and pool configuration.

          

          

            
Product and operations

            
Requirements, user journeys, tickets, incidents, traces, metrics, dashboards, benchmarks, support issues, roadmap, adoption data, and business KPIs.

          

        

        

          The strongest review input includes both code-level evidence and product-level intent. Architecture quality cannot be assessed from diagrams alone.
